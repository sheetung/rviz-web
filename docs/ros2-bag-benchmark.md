# ROS2 适配分离：真实 rosbag 验证

测试日期：2026-09-14。

## 结论

- 当前 ROS2 后端能从现有 Humble bag 同时接收三路点云，并通过 WebSocket
  输出有效的紧凑 XYZ 二进制帧；四轮订阅确认均成功，无协议错误。
- 两版共同接收到的 602 个不同时间戳点云帧，完整 WebSocket 二进制帧 SHA-256
  全部一致。覆盖 Avia 246 帧、Mid360 240 帧、Ouster 116 帧。
- **本轮没有证明架构拆分带来性能提升。** CPU、内存、延迟略有上升，吞吐也略有
  上升；只有每版两轮且接收负载存在波动，不能认定这些差异是重构造成的。
- Ouster 仅约 4–5 Hz；绕过整个后端、直接 rclpy 订阅也只有 4.35 Hz，说明
  本环境存在后端之外的接收瓶颈，不能把降帧全部归因于转换或 WebSocket。
  尚未进一步区分 rosbag 调度、DDS 大消息传输、QoS 和虚拟机资源影响。

## 方法与环境

- VMware 虚拟机，8 vCPU，宿主 CPU 标识 Intel Core i5-13500TE；
  Linux 6.8.0-138-generic，ROS2 Humble，Python 3.10.12。
- uvicorn 0.51.0、websockets 16.1.1、psutil 5.9.0。
- `ROS_DOMAIN_ID=197`、`ROS_LOCALHOST_ONLY=1`，后端监听 `127.0.0.1:18081`。
  只播放点云，不发布运动控制消息。
- 运行顺序 A/B/B/A，各轮重启后端和 bag，从 bag 开头按 1 倍速播放。
  收齐三话题后预热 5 秒，再测量约 20 秒；不是完整 66 秒回放测试。
- CPU 为后端进程 user+system 时间差 / 墙钟时间，100% 表示一个 CPU 核；
  不包含独立的播放器、接收器进程或全系统 CPU。
- RSS 每 0.5 秒采样；应用层 ping 每 0.5 秒发送，测量收到 pong 的往返时间。
- 吞吐为收到的完整 WebSocket 二进制帧大小，不含 TCP/WebSocket 帧头。
  客户端检查 RVPC 标识、版本、XYZ 字段、12 B point_step 和数据长度，并记录哈希。
- SHA-256 比较按话题和消息原始时间戳匹配，包含预热阶段；不代表所有 bag 帧都收到。

## 限制与下一步

- 没有启动真实浏览器，不涉及 Worker、GPU、渲染 FPS 或用户可见延迟。
- bag 不含 TF；三个传感器使用不同 frame_id，不能据此确认多雷达空间配准正确。
- 未覆盖多客户端、慢客户端、自定义消息、控制发布、多设备 DDS 或容器网络。
- 两版在 SIGINT 退出时均记录 `ExternalShutdownException` 为 fatal，随后正常退出。
  这是停止阶段日志问题，不是测量期间崩溃；应单独规范预期 ROS 关闭异常处理。
- 优先调查 Ouster 6 MiB/帧的大消息接收：对照不同播放速率、QoS、DDS 实现和
  非虚拟机环境，并分别计数源端发布、ROS 回调、转换和发送帧数。
- 后续性能优化应单独提交，用相同数据复测；本次边界重构以职责清晰、输出一致
  为验收结果，不标记为性能优化完成。

## 追加压力测试：倍速、并发与停读客户端

同日继续增压，沿用上面的两版快照与依赖。使用独立 Domain 198、端口 18082，
bag 循环播放，每轮收齐订阅确认后预热 3 秒。默认每话题 10 Hz 转发上限没有修改。
倍速为播放器目标速率，并不表示 DDS 实际收到相应频率；循环切换也会影响流量。
每个正常客户端都订阅三话题并每 0.5 秒 ping；停读客户端确认订阅后停止调用
recv，接收队列 max_queue=1。正常客户端仍检查每个二进制帧的字段与长度。

### 发现一：传输层缓冲绕过应用背压

本机安装的 Uvicorn 0.51.0 在 `--ws auto` 时选中 `websockets-sansio`。
检查已安装源码，其发送路径调用 `transport.write(...)`，没有等待写缓冲排空。
因此应用层 `wait_for(send_bytes(...), 2 秒)` 可以很快返回，而停读连接的数据
继续累积于传输缓冲。应用最新帧队列有界，不等于整个发送链路的内存有界。
这一问题在前后两版均复现，不是本次 ROS2 拆分特有。

仅在测试命令中改用 `--ws websockets` 做诊断对照，业务代码和系统参数均不变：

- 1 倍速、1 正常 + 1 停读、20 秒：RSS 首/尾均值 **130.52 → 127.92 MiB**，
  峰值 **140.53 MiB**，正常客户端 40 次 ping 全部应答。
- 8 倍速、8 正常 + 2 停读、60 秒：CPU **52.58%**，总吞吐 **109.22 MiB/s**，
  RSS 首/尾均值 **194.10 → 238.09 MiB**，峰值 **263.06 MiB**；正常客户端
  **960 次 ping 全部应答**，最差客户端 P95 **32.11 ms**，单次最大 **42.91 ms**。
  各客户端三话题约 **6.91 / 6.91 / 6.78 Hz**。没有重现超过 1 GiB 的快速积压，
  但 60 秒内存仍有上升，不能据此证明长时间无泄漏。
- 服务端出现预期的发送超时日志；停读客户端没有继续读取关闭帧，
  不能凭其本地 State.OPEN 判断服务端清理是否完成。

这支持把传输层背压作为修复重点。尚未把诊断参数应用到 `start.sh`、Docker
启动入口或程序入口；需要单独修复并增加真实慢连接回归，不能把该对照算作默认
部署已经修好。测试客户端和播放器与后端同机，结果不代表真实局域网部署容量。

### 发现二：断订阅与转换完成之间的竞态

当前版本 4 倍速、4 客户端测试在测量结束、客户端集中断开后出现：

```text
Ros2Adapter._on_message_received
await self._message_sink(topic, payload, self._subscription_types[topic])
KeyError: '/avia/livox/lidar'
```

进入转换前检查订阅存在，但 `await asyncio.to_thread(...)` 期间最后一个客户端
可以断订阅并清除 `_subscription_types`；恢复后直接索引触发异常。旧版对应路径
使用 `.get(topic, "")`，没有这一直接索引异常点。这是本次拆分引入的竞态，
不能把全部日志归为正常关闭噪声。异常被处理循环捕获，没有导致进程崩溃。
应对转换完成后的订阅有效性进行重检，并用确定性的取消订阅交错测试覆盖。

另观察到断线时继续发送的错误日志以及之前的 SIGINT 关闭异常，应一并规范
生命周期处理。本次仅测试、诊断和记录，没有修改这些业务行为。

追加测试的本机临时证据保存在 `/tmp/rvizweb-stress-XZnaDf/`：
`stress.py`、`isolate.py`、`transport.py`、`results.json`、`isolation.json`、
`transport.json`、各轮 JSON 与日志。JSON 的 `passed` 只表示正常客户端测量检查，
不包含事后日志审计或长期内存稳定性；全局结论以上述问题记录为准。
