# 当前 ROS2 框架：RTSP 与点云混合测试

测试日期：2026-09-14。只测试 `320a14d` 加当前未提交的 ROS2 适配分离，
没有运行旧框架。测试副本的 `backend/management/app` 与工作区一致。

## 结论

- 实际 RTSP → FFmpeg → HTTP MJPEG 链路可用；单路和四路输出均约 12 fps，
  JPEG 首帧可完整解码为 640×360。
- 四路转码叠加三路点云、8 倍回放、8 个正常点云客户端，30 秒测量完成：
  视频约 12 fps，480 次心跳全部应答，但点云仅约 3.7–3.8 Hz。
- 同框架无视频对照的点云约 4.9–5.0 Hz。混合场景吞吐较低，但每场景仅一轮，
  不能排除播放器、DDS、虚拟机负载和测量窗口差异，不能直接认定因果或容量上限。
- 会话/重复流限额、生效中的会话删除、源断流、手动重开均通过本轮检查。
  每轮清理后后端的 FFmpeg 子进程数为 0。
- 点云断订阅竞态在本轮再次出现；RTSP 可用不等于整个框架无已知缺陷。

## 环境与隔离

- 机器与依赖沿用 [点云压力报告](ros2-bag-benchmark.md)：ROS2 Humble、Python 3.10、
  Uvicorn 0.51.0；本轮保持默认 `--ws auto`，没有引入停读的 WebSocket 客户端。
- FFmpeg 4.4.2。临时 GStreamer RTSP Server 1.20.1 绑定 `127.0.0.1:18554`，
  后端绑定 `127.0.0.1:18083`，ROS_DOMAIN_ID=199、ROS_LOCALHOST_ONLY=1。
- 模拟源为 H.264、1280×720、30 fps、GOP 30；一个共享源，多个独立视频会话和
  FFmpeg 转码进程，**不是四台真实摄像头**。基础画面为移动球，压缩后负载较小。
- 后端保持默认 TCP、12 fps、宽 640、JPEG quality=5、最多 4 会话/4 转码，
  同一会话最多一条活动流。没有提高系统配额或修改 `.env`。
- 默认策略实际拒绝回环 RTSP 地址，符合预期。仅测试副本的入口将代码级
  `Settings.rtsp_allowed_hosts` 精确设为 `127.0.0.1`；其他安全策略不变。
  本轮成功不代表未经放行的真实内网摄像头可以直接连接。
- 缺少的 GStreamer RTSP 库通过发行版包解压到 `/tmp` 使用，没有安装系统服务。
  原始 rosbag 和工程业务代码均未修改。

## 计量方法

每场景完成会话探测、获取视频首帧和点云发现后，预热 3 秒，再计量 20–45 秒。
源启动和探测不计入稳态 CPU，但另外记录耗时。基础场景共用一次后端启动，
每场景清除会话和订阅；补充对照重新启动同一框架。

CPU 100% 表示一个核，后端与其 FFmpeg 子进程分列；不包含模拟视频源、播放器、
HTTP/WS 接收器或全系统开销。RSS 峰值也分列，不能简单相加当作同时发生的峰值。
JPEG 首帧完整解码，后续按 JPEG 边界计数；点云检查 RVPC 帧头与数据长度。
视频 FPS 是 HTTP 接收帧率，不是浏览器渲染 FPS。

| 4 视频，无点云 | 25s | 7.38% | 19.88% | 70.50 MiB | 282.43 MiB | 11.97–12.01 | — | — |

点云三个话题按 Avia / Mid360 / Ouster 顺序：

- 4 视频 + 8×/8 客户端：3.84 / 3.74 / 3.74 Hz，480/480 pong。
- 3 正常视频+1停读 + 4×/4 客户端：7.30 / 7.30 / 5.84 Hz，240/240 pong。
- 无视频 8×/8 客户端：5.04 / 5.04 / 4.94 Hz，480/480 pong。

会话创建内部探测约 1.22–1.64 秒，随后流请求到首帧约 1.32–1.43 秒；
这两个阶段是串行的，不能把约 1.3 秒称为从输入 URL 到出画的总耗时。

基础球形画面每路仅约 0.021 MiB/s；基础停读场景不足以证明高码率下的背压能力，
因此另补复杂画面及小接收缓冲的停读实验。

## 复杂画面与停读补测

源改为 SMPTE 合成测试画面，仍为 720p/30 fps H.264。四个独立会话，三个正常
视频接收器，第四个设置 SO_RCVBUF=4096 并在 HTTP 响应头后暂停读取；叠加
4 倍速三路点云和 4 个正常 WebSocket 客户端，持续测量 45 秒。

- 正常视频每路 **12.00 fps / 0.153 MiB/s**，约为基础画面的 7 倍输出带宽。
- 后端 CPU **39.10%**，FFmpeg 合计 **27.30%**。
- 后端 RSS 峰值 **217.94 MiB**，FFmpeg 合计峰值 **283.16 MiB**；
  合计 RSS 首/尾 5 秒均值 **495.82 → 494.19 MiB**。
- 点云总吞吐 **55.06 MiB/s**，三话题 **7.75 / 7.70 / 6.57 Hz**。
- **360/360 pong**，P95 **35.85 ms**；会话限额和重复流仍返回 429。
- 结束后读取线程全部退出，后端 FFmpeg 子进程为 0。

这一短测没有复现此前 WebSocket 停读的快速内存积压，不能据此证明任意码率、
任意时长或大量慢视频连接都安全。MJPEG 使用 HTTP StreamingResponse，与点云
WebSocket 的传输实现不同，不应把两者的背压结论互相套用。

## 错误路径和资源清理

- 第 5 个视频会话：429；已有流的同会话再次 GET：429。
- 不存在的 RTSP 路径：504；这验证源不可用处理，不等于认证失败、网络黑洞超时
  或全部 FFmpeg 错误分支已经覆盖。
- 关闭源后，正在读取的 MJPEG 流结束，FFmpeg 子进程降为 0。
- 重启源后，再次 GET 同一个未删除会话，首帧约 1.36 秒恢复。
  **这是显式重开，不是自动断流重连验证。**
- 删除活动会话后读取线程退出，FFmpeg 为 0；访问已删除流返回 404。
- 所有正常客户端测量期间无协议错误或未应答 ping。
- 测量结束的断订阅阶段仍出现 ROS2 Adapter 的 `_subscription_types[topic]`
  KeyError，另有已知 SIGINT 关闭日志问题；详见前一份报告，尚未修复。

## 范围限制与证据

或 300 秒会话 TTL 验证。当前结果是后端链路与有限负载的实测，不是生产容量承诺。
